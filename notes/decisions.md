# Журнал решений (ADR)

Значимые решения проекта в хронологическом порядке. Новые записи — сверху.

## 2026-08-13 — Ревью новой 4-модельной архитектуры: автопересчёт цены и заморозка снимка

- **Контекст:** после рефакторинга (Room/User/Stay/Report, JSONB payments/services/reviews) в `Stay` остался `before_validation :freeze_prices` с `on: :create` + `if: :price_settings_changed?` на одном методе — при регистрации колбэков второй вызов перекрывал первый, и цена вообще не считалась (все `total_price` = 0).
- **Решение:** `before_validation :freeze_prices, if: :price_settings_changed?` (единый колбэк: `new_record? || stay_settings_changed?`). При создании Stay цена/снимок считаются атомарно из номера; при смене дат/номера у не-заселённых пересчитывается; ручной `total_price` после заселения не трогается.
- **Статус:** ✅ реализовано

## 2026-08-13 — Удаление omniauth (VK/Яндекс)

- **Контекст:** после слияния Гость/Администратор в единый `User` (devise, роль guest/admin) omniauth-стратегии (`lib/omniauth`) остались мёртвым кодом: `User` без `:omniauthable`, маршрутов oauth нет, `config/initializers/devise.rb` регистрировал провайдеры с фейковыми ключами, а `config.autoload_lib` ломал `zeitwerk:check` (константа `Omniauth` vs `OmniAuth`).
- **Решение:** удалены `config.omniauth` из devise.rb и `lib/omniauth/strategies`; Gemfile не тронут (gem'ы не мешают, отсутствуют в routes).
- **Статус:** ✅ реализовано

## 2026-08-12 — Штраф за неявку (п.9 дорожной карты)

- **Контекст:** sweeper уже отменял no-show и слал напоминание за сутки; не было штрафа — план «штраф (связь с депозитом из п.1)» реализован на балансе оплат из п.1 (отдельных депозитов нет).
- **Решение:** поле `bookings.no_show_fee` (decimal) — цена первой ночи (из снимка `booking_nightly_prices`, фолбэк `total_price / ночи` для броней до внедрения снимка). `BookingSweeperJob` начисляет его при автоматической отмене no-show (pending/confirmed с прошедшим `check_in`) идемпотентно (повторный прогон не трогает). `Booking#due_amount = total_price + no_show_fee - paid_amount`, поэтому штраф виден в «Долге» карточки, списка броней и CSV-экспорта; в карточке — отдельная строка «Штраф за неявку».
- **Статус:** ✅ реализовано (502 теста, rubocop 0)

## 2026-08-12 — Отчёты за период (п.8 дорожной карты)

- **Контекст:** CSV-экспорт был только у bookings/guests; операционная картина (факт vs план, загрузка по категориям и по ночам) отсутствовала.
- **Решение:** сервис `Reports::PeriodReport` (план = ночная раскладка из снимка цены `booking_nightly_prices` по активным статусам, факт = реальные оплаты `Payment` по дате, занятость = активные брони, перекрывающие ночь; таблицы по категориям и по ночам, итоги; период ограничен 92 днями, `from..to` включительно).
  - План строится по снимку цены (сортировка с п.2): брони до внедрения снимка в плане не учитываются — для молодого кода это допустимо, зафиксировано как известное ограничение.
  - `Admin::ReportsController` (index + export CSV через `ReportsCsvExporter`), пункт «Отчёты» в sidebar, кнопка «Отчёт за этот месяц» на дашборде.
- **Статус:** ✅ реализовано (499 тестов, rubocop 0)

## 2026-08-12 — Журнал статусов номеров и автоматическая уборка (п.7 дорожной карты)

- **Контекст:** `room.status` менялся без истории (в отличие от `BookingAuditLog`); после выезда гостя номер сразу становился `available`, а план предусматривал рабочий процесс уборки.
- **Решение:**
  - Модель `RoomStatusLog` (room, from_status, to_status, created_at). Источники записи: ручная смена через `Room#after_update` (обычный формат) и автоматическая синхронизация в `RoomStatusSync`, которая пишет запись явно, потому что там `room.update_column` (обход колбэков) — иначе журнал был бы неполным.
  - Смена семантики выезда: `checked_out` → номер переходит в `cleaning` (а не `available`), отмена после заселения → `available`. Номер в `cleaning` не резервируется, пока админ не нажмёт «Уборка завершена» (`PATCH /admin/rooms/:id/complete_cleaning` → `available`).
  - UI: кнопка «Уборка завершена» прямо в списке номеров (только для `cleaning`) + страница истории `/admin/rooms/:id/status_history`.
- **Статус:** ✅ реализовано (489 тестов, rubocop 0)

## 2026-08-12 — Админ-уведомления о новых бронях и отзывах (п.6 дорожной карты)

- **Контекст:** `Notification` умел слать только пользователю (`user_id null: false` + письмо); админ узнавал о новой броне, лишь открыв дашборд (email уже был, но в приложении нет).
- **Решение:** уведомления «для администрации» — отдельный канал в той же таблице:
  - `notifications.user_id` стал необязательным (`change_column_null true`), новый столбец `to_admin` (boolean, default false, индекс `[to_admin, read_at]`). `Notification#deliver_email` пропускает `to_admin`-уведомления (письма только пользователям).
  - Создание: `BookingNotifier#notify_admins_of_new_booking` и `Review#notify_admins_of_new_review` — помимо `AdminMailer` создают `Notification` (kind `new_booking`/`new_review`, notifiable = бронь/отзыв). Бронь, созданная самим админом, не порождает bell-уведомление: `Admin::BaseController` держит `Thread.current[:current_administrator]` на время запроса, отличается в notifier.
  - UI: колокол «Уведомления» в topbar админки с бейджем непрочитанных (`@admin_unread_count` считает `Notification.for_admin.unread.count` при каждом админ-запросе), страница `/admin/notifications` (список, «Открыть» — переход к брони/списку отзывов через `notification_target_path`, «Прочитать», «Прочитать все»).
- **Статус:** ✅ реализовано (483 теста, rubocop 0)

## 2026-08-12 — Согласие на обработку персональных данных (п.5 дорожной карты)

- **Контекст:** отель хранит паспортные данные гостей, но никак не фиксирует согласие на обработку ПДн (152-ФЗ). Нужен учёт согласий и явное соглашение в публичной форме брони.
- **Решение:**
  - Новая модель `ConsentLog` (guest_id, signed_at) — «счётчик согласий»: запись создаётся при каждой успешной публичной брони (гость уже сохранён в той же транзакции `BookingCreator`). На карточке гостя показывается число согласий. Журнал восстановим для отчёта по 152-ФЗ.
  - Публичная форма брони: обязательный чекбокс «Я согласен на обработку персональных данных (152-ФЗ), включая паспортные данные» + ссылка на страницу `/privacy` с политикой ПДн (роут → `PublicSiteController#privacy`, статичная вьюха; ссылка также в футере).
  - Требование согласия принудительно в **публичном** пути: `BookingCreator` получает `consent_given:` и без него добавляет ошибку брони «Необходимо согласие на обработку персональных данных». Админка (`Admin::BookingsController#create`) не использует `BookingCreator` и не затронута — админ может вносить брони без согласия.
  - Согласие хранится на уровне гостя, а не брони: одно согласие = один факт подписи; повторные брони создают новые записи (растёт счётчик). IP/пользователь не фиксируются — минимально необходимый набор данных.
- **Статус:** ✅ реализовано (478 тестов, rubocop 0)

## 2026-08-12 — Карточка гостя и слияние дублей (п.4 дорожной карты)

- **Контекст:** у гостя был только набор полей, дохода и истории в одном месте не существовало; `find_or_initialize_by(email)` в публичной брони мог плодить дубли (пустой email, разные написания, ручной ввод в админке).
- **Решение:**
  - Карточка `/admin/guests/:id` (не было `show` у `Admin::GuestsController`): история броней (статусы, суммы, оплачено/долг), сумма за всё время (`total_spent` = сумма по `payments` через брони), число завершённых заездов, VIP-бейдж. Кнопка «Карточка» в списке гостей.
  - `is_vip` + `preferences` у гостя (форма, колонки VIP/Предпочтения в CSV).
  - Слияние дублей: `Guest#possible_duplicates` — совпадение по email (без учёта регистра, т.к. уникальность email регистро-зависимая), телефону или паспорту; `Guest#merge_into!` в транзакции переносит брони (`update_all guest_id`) и объединяет профиль: VIP-статус по OR, пустые поля дополняются, заметки склеиваются. Кнопка «Объединить с этим гостем» на карточке; `dependent: :restrict_with_error` не мешает удалению, т.к. брони уже перенесены.
  - Телефон не имеет валидации уникальности — основной сценарий дублей; email не может дублироваться через модель.
- **Статус:** ✅ реализовано (470 тестов, rubocop 0)

## 2026-08-12 — Закрытые даты и минимальный срок (п.3 дорожной карты)

- **Контекст:** цена не считается двумя способами, но отель не мог закрыть ночь (ремонт/переселение коллектива) и не мог задать минимальный срок проживания в высокий сезон; публичный виджет предлагал недоступные даты, форма брони их принимала.
- **Решение:**
  - `PricePeriod#min_nights` (optional, ≥ 1) — минимальный срок для любого пребывания, пересекающего период. `StayRules#min_nights_between` берёт максимум среди периодов, покрывающих ночь; для дней закрытия период не нужен.
  - Новая модель `ClosedDate` (date, unique; reason) — глобальные закрытые ночи отеля. `StayRules#closed_dates_between` считает ночи `[check_in, check_out)` и при наличии пересечения отклоняет пребывание целиком.
  - Подключено в обоих публичных путях: `RoomAvailability` (виджет: `Failure` с человеко-читаемой строкой → 422 в `error`), `BookingCreator` (форма брони: ошибки «отель закрыт на выбранные даты» / «минимальный срок проживания составляет N ночей»). Админка может вносить брони вручную поверх ограничений — проверки только в публичных сервисах.
  - Админка: CRUD `/admin/closed_dates`, `min_nights` в форме и списке ценовых периодов, пункт «Закрытые даты» в sidebar.
- **Статус:** ✅ реализовано (457 тестов, rubocop 0)

## 2026-08-12 — Оплаты по брони и снимок цены (п.1 + п.2 дорожной карты)

- **Контекст:** выручка дашборда считалась «по тарифу» (сумма `total_price` выехавших), а не по реально принятым деньгам; `BookingPricing#calculate_total_price` пересчитывал цену существующей брони по **текущим** `PricePeriod`, поэтому изменение сезонного коэффициента задним числом молча меняло цену старых броней.
- **Оплаты (`Payment`):** новая модель (amount, method `cash`/`card`/`transfer`, paid_at, note), CRUD вложен в админ-бронь (`/admin/bookings/:id/payments`), блок в карточке брони с балансом «Оплачено / Долг / Итого», колонка «Оплачено» в списке, выручка дашборда = сумма оплат за месяц (+подпись «по тарифу N»), CSV-экспорт получает колонки «Оплачено, ₽» и «Долг, ₽». Предоплата/доплата/расчёт — ручные действия администратора; автогенерации оплат при смене статуса нет (нет понятия депозита).
- **Снимок цены:** ночная раскладка замораживается в таблицу `booking_nightly_prices` (unique `[booking_id, date]`) при каждом пересчёте цены — создании, смене дат или номера. Решение «снимок при пересчёте, а не при подтверждении» (в отличие от исходной формулировки): расчёт и заморозка атомарны в одном before_save, исключается разрыв «цена посчитана по новому тарифу, снимок старый». На брони добавлен `price_frozen_on`; разбивка на странице брони — из снимка с пометкой «цена зафиксирована по тарифу на дату X и не меняется при изменении тарифов» (раньше — живой `NightlyPricing`). Ручные скидки (`total_price` правкой) снимок не трогают.
- **Статус:** ✅ реализовано (426 тестов, rubocop 0)

## 2026-08-12 — dry-rb: консолидация, а не расширение (рефакторинг-план)

- **Контекст:** запрос «refactor with dry-rb». Адверсариальный планинг (5 ролей × 3 раунда кросс-атак) на codebase hotel_cms.
- **Решение:** новых dry-гемов НЕ добавляем. dry-monads 1.10 уже установлен и актуален; dry-system/dry-rails (спящий 0.7.0/2022), dry-container (заморожен), dry-transaction (официально deprecated → dry-operation), dry-validation поверх AR-валидаторов — отклонены. dry-statemachine/dry-states на rubygems НЕ существуют (проверено) — ручной `StatusTransitionable` остаётся.
- **Объём:** (1) characterization-спек `room_availability_spec.rb` (покрытие было пустым); (2) де-дуп парсинга дат — `DateParams.parse` (3 места: bookings_controller, room_availability, application_helper); (3) фикс silent `200 []` — `value_or([])` на available_rooms/admin available → `Failure(:invalid_dates)` / `Failure(:invalid_range)` = 422, пустой результат = `200 []`; (4) коллапс симметричного распаковывания Result в BookingsController#create → `result.value_or(result.failure)`.
- **Вне рамок:** типы денег (закреплены спеками: admin_bookings_spec `"4000.0"`, public_bookings_spec `eq(2500.0)`), колбэки/валидации AR, CSV-экспортёры, state machine, слаггер, constraint_guarded.
- **Статус:** ✅ реализовано (404 теста, rubocop 0). Валидация дат разведена на `:invalid_dates` (непарсится) и `:invalid_range` (обратный диапазон) — оба дают 422 на JSON-эндпоинтах, пустой search — `200 []`.

Важный нюанс shared-примера удаления: `change(model_class, :count)` снимает значение ДО выполнения блока, поэтому `record` создаётся вне `expect { }` (иначе создание и удаление внутри блока дают 0).

## 2026-08-12 — Ценовые периоды и коэффициент выходных (динамические цены)

- **Контекст:** цена при бронировании была фиксированной (`nights × price_per_night`) — нельзя задать сезонные повышения и выходные надбавки; отель терял выручку в высокий сезон.
- **Решение:**
  - Модель `PricePeriod` (name, starts_on, ends_on, multiplier) с валидацией непересечения периодов и `multiplier > 0`; serialize-скоп `covering(date)` + `PricePeriod.multiplier_on`.
  - Сервис `NightlyPricing` (room, check_in, check_out): считает цену по каждой ночи как `base × seasonal_multiplier × weekend_multiplier`; выходные — пятница и суббота (wday 5,6), коэффициент берётся у номера (`weekend_multiplier`, по умолчанию 1.0). Периоды для диапазона грузятся ОДНИМ запросом (интервальный фильтр между первой и последней ночью), а не запросом «на ночь» — без N+1 при подборе номеров.
  - `Booking#calculate_total_price` переведён на `NightlyPricing` (по-прежнему только при создании/смене дат/номера, ручные скидки не затираются); `RoomAvailability` добавляет `total_price` к JSON; на странице брони — справочная разбивка «стоимость по ночам».
  - Админка: CRUD `/admin/price_periods`, поле «коэффициент выходных» в форме номера.
- **Статус:** ✅ реализовано (351 тест, rubocop 0)

## 2026-08-12 — Защита целостности на уровне БД

- **Контекст:** Rails-валидации не защищают от гонок (два одновременных запроса могут пройти валидацию непересечения); отзывы можно было оставлять повторно; услуги можно было заказать на прошедшую дату.
- **Решение:**
  - Exclusion constraint `no_overlapping_bookings` на `bookings` (`btree_gist`, `daterange(check_in, check_out)` + `WHERE status <> 'cancelled'`) — двойное бронирование невозможно на уровне БД, семантика совпадает со скопом `active_overlapping`.
  - Unique index `index_reviews_on_user_reviewable_unique` на `(user_id, reviewable_type, reviewable_id)` + валидация «один отзыв на объект от одного пользователя».
  - Валидация `service_date` не в прошлом у `ServiceOrder` (заказы создают только пользователи публичного сайта).
  - Концерн `ConstraintGuarded` — переопределяет `save`/`save!` и превращает `PG::ExclusionViolation`/`PG::UniqueViolation` в понятную ошибку валидации (вместо 500 при гонке).
- **Статус:** ✅ реализовано (194 теста, rubocop 0)

## 2026-08-12 — Аудит бизнес-логики, баги и рефакторинг с DRY-rb

- **Контекст:** найдено 7 багов: телефон гостя не копировался из пользователя (мёртвое условие `guest.phone.present? && guest.phone.blank?`); номера со статусами `maintenance`/`cleaning` предлагались к бронированию; при неудачной брони оставались «фантомные» пользователь и гость (сохранение до валидации брони); не было контроля переходов статусов (можно заселить отменённую бронь, отменить заселённую без освобождения номера); `guests_count` принимал 0; отзыв можно было оставить на любой полиморфный объект; при очистке slug страница конфликтовала сама с собой (`-1`).

  - Админ-действия переведены на `transition_to` с понятными alert'ами (`Admin::BaseController#transition_alert`).
